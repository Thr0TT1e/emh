# Отчёт по безопасности EMH Backend

## 🔴 Высокий приоритет

### H1. `/metrics` публично доступен из интернета
`cmd/api/server.go:73` монтирует `/metrics` без аутентификации с комментарием «в production защищается Caddy (IP whitelist)» — но в `infra/podman/Caddyfile:24-26` блок `api.neverforgotten.ru` проксирует **всё** на `:3480` без каких-либо ограничений путей. Итог: любой может смотреть статистику попыток аутентификации, имена/модели LLM-провайдеров, бизнес-метрики. Это ещё и усилитель для H2.

**Рекомендация:** добавить в Caddy `handle /metrics { respond 403 }` (или `remote_ip` allowlist) до `reverse_proxy`, либо токен/basic-auth в приложении. Проверить фактический продакшен-Caddyfile — возможно, он отличается от этого.

### H2. Cardinality-bomb в Prometheus через Login (без аутентификации)
`internal/usecase/auth_usecase.go:76-81` — метрики `AuthTokensIssuedTotal` и `AuthActiveSessions.WithLabelValues(username)` инкрементируются **до** проверки пароля. Атакующий, спамя `Login` с произвольными username (лимит 5/мин на IP обходится ботнетом/IPv6-пулом), создаёт неограниченное число label-значений в GaugeVec (`internal/metrics/auth.go:35-43`) → раздувание памяти Prometheus и деградация сбора метрик. Плюс искажение данных: неудачные попытки считаются «выданными токенами» и «активными сессиями». В `Refresh` (строки 101-102) та же ошибка — инкремент до валидации токена.

**Рекомендация:** перенести все инкременты после успешной аутентификации; для `AuthActiveSessions` убрать label `username` или ограничить известными админами.

### H3. MCP-сервер в HTTP-режиме — без авторизации и таймаутов
`cmd/mcp/main.go:129-136`: `--transport=http` поднимает SSE-сервер на `:3481` (все интерфейсы) с открытым `TODO: добавить middleware авторизации`. Инструменты включают создание заявок и LLM-экстракцию (расход токенов внешних провайдеров). Плюс `http.ListenAndServe` без `ReadHeaderTimeout` — Slowloris.

**Рекомендация:** до реализации авторизации (переиспользовать `AUTH_API_KEYS`/библиотеку интерцептора) — не запускать HTTP-режим на проде; сменить дефолт адреса на `127.0.0.1:3481`; обернуть в `http.Server` с таймаутами как в `cmd/api/main.go:67-74`.

### H4. Секреты в git-истории
`config.yaml` сейчас не трекается (в `.gitignore` — это хорошо), но **ранее был закоммичен**: в коммите `f4a38be` («Настройка для прода») есть реальный bcrypt-хеш пароля админа (`$2a$10$tnVLd...`). Хеш подбирается офлайн. Текущий локальный `config.yaml:16` содержит пароль БД `bf3b8c18...` и `ip_pepper` — проверьте, что эти значения не совпадают с продакшеновыми.

**Рекомендация:** сменить пароль админа (хеш мог быть скомпрометирован, репозиторий публичный на codeberg); убедиться, что прод-пароль БД и pepper отличаются от локальных; при необходимости вычистить историю (`git filter-repo`) и ротировать все секреты, попавшие в коммиты.

## 🟡 Средний приоритет

### M1. Роли не enforced — любой API-ключ = полный админ
`internal/delivery/interceptor/auth.go:158-170`: для валидного API-ключа роль не проверяется — ключ с любой ролью проходит на все admin-сервисы. `internal/usecase/api_key_usecase.go:38` дефолтит роль в `"admin"`, статические ключи (`auth.go:147`) тоже дают полный доступ без сроков действия. Роли сейчас декоративны.

**Рекомендация:** проверять `key.Role`/`claims.Role` в интерцепторе для admin-сервисов; статические ключи — только для аварии, с плановым ротационным сроком.

### M2. Admin-сервисы исключены из rate limiting
`internal/delivery/middleware/ratelimit.go:81-84` — пути `*AdminService` полностью bypass'ят лимитер. Каждый запрос с существующим keyID запускает bcrypt (~60-100мс CPU): зная UUID keyID (утечка логов?), можно жечь CPU без ограничений; брутфорс секрета тоже без lockout.

**Рекомендация:** применять к admin-группе повышенный лимит (например, 60/мин) вместо полного отключения.

### M3. MinIO Console открыта в интернет
`infra/podman/Caddyfile:68-70`: `console.minio.neverforgotten.ru` проксируется без IP-ограничений — атакующая поверхность (брутфорс, CVE консоли).

**Рекомендация:** `remote_ip` allowlist / VPN / basic auth поверх.

### M4. Сырой IP в аудите неудачных попыток
`interceptor/auth.go:225` — `recordFailure` пишет в `auth_audit_log` **сырой** IP, тогда как `recordSuccess` (строка 204) пишет HMAC-хеш. Это расходится со заявленным «IP hashing в аудите» и создаёт PII-долг (таблица к тому же без ротации — долг #14).

**Рекомендация:** хешировать единообразно; сырой IP (если нужен для расследований) — в отдельной таблице с коротким TTL.

### M5. LLM: prompt injection и приватность
`internal/usecase/extraction_usecase.go:180-182` — пользовательский текст вставляется в промпт без ограничений. Human-in-the-loop через Submission — правильная митигация, но результат авторазносится по полям админ-формы (включая `warnings`), т.е. внедрённый текст увидит модератор. Также: промпт+ответ с данными заявителей хранятся в `llm_extraction_logs` бессрочно и уходят к сторонним провайдерам (OpenRouter/gptunnel) — стоит оформить это как политику хранения. Размер входного текста ограничен только 4MB общего лимита → расход токенов (admin-only, но всё же).

**Рекомендация:** лимит длины текста в proto-валидации (например, 50КБ); TTL/партиционирование для `llm_extraction_logs`; экранировать `warnings` при выводе.

### M6. CORS на S3 отражает произвольный Origin
`infra/podman/Caddyfile:45,55` — `Access-Control-Allow-Origin: {http.request.header.Origin}` + `Allow-Headers: *`. Для presigned PUT это терпимо (URL сам — креденшил), но неограниченное отражение Origin не нужно.

**Рекомендация:** белый список доменов проекта.

## 🟢 Низкий приоритет (hardening)

- `internal/llm/openai_compatible_provider.go:88` — `io.ReadAll` тела ошибки без лимита; обернуть в `io.LimitReader` (проверить и anthropic/ollama).
- `internal/auth/jwt.go` — issuer проставляется, но при валидации не проверяется; добавить `jwt.WithIssuer("emh")` + `WithExpiration()`.
- Нет ограничения числа активных refresh-токенов на пользователя — копятся до экспирации (7 дней).
- Caddy: нет HSTS/`X-Content-Type-Options` на доменах.
- Статические ключи сравниваются через map-lookup (не constant-time) — приемлемо только для случайных ключей 32+; задокументировать.
- `db.url` с `sslmode=disable` — для контейнерной сети допустимо, но зафиксируйте это явно как осознанное решение.
- Баг из снапшота `p.Status` → `p.Decision` — **уже исправлен** (`submission_usecase.go:96`), обновите снапшот. Аналогично `c.LLM.Endpoint/APIKey/Model` в `overrideFromEnv()` уже убраны.

## ✅ Что сделано отлично (подтверждено кодом)

- **SQL полностью параметризован**: все 16 репозиториев на squirrel-placeholder'ах; ILIKE экранируется `escape.LIKE` + `ESCAPE '\'` (`hero_repository.go:472-478`); `websearch_to_tsquery` параметризован; ORDER BY — только статические строки. SQL-инъекций не нашёл.
- Constant-time login с dummy-хешем, ротация refresh + детект кражи с `RevokeAllForUser`.
- JWT: проверка семейства алгоритмов (нет `alg=none`), секрет ≥32 символов + blocklist слабых паттернов (`config.go:456-534` — редкая тщательность).
- Decompression-bomb: 50MB `LimitReader` + проверка габаритов **до** полной декодировки (`thumbnail_worker.go:41-45,245-264`), и Caddy-лимит 50MB на S3-загрузку — эшелонированная оборона.
- MIME-whitelist + Content-Type в подписи presigned URL + серверная генерация ключей (UUID, без path traversal).
- SMTP: CRLF-санитизация, STARTTLS, нормализация полей contact-формы, honeypot, дедупликация, HMAC-хеш IP с pepper.
- Trusted proxies: rightmost-untrusted XFF + валидация CIDR при старте.
- Внутренние ошибки не утекают клиентам (`delivery/v1/errors.go:123-151`).
- LLM-эндпоинты только из конфига → SSRF через API недоступен; API-ключи только из env.
